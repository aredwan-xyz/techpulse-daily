PROMPT_TITLE: Bulletproof Test Suite Architect

THE_PROMPT:
Act as a Senior QA Automation Engineer and Software Architect. Generate a production-grade, comprehensive test suite for the provided code snippet or feature requirement.

**Input Code / Specifications:**
```
{CODE_OR_FUNCTION}
```

**Testing Specifications:**
- **Testing Framework:** {TESTING_FRAMEWORK} (e.g., Jest, PyTest, JUnit 5, Vitest, Go testing)
- **Test Scope:** {TEST_TYPES} (e.g., Unit, Integration, Edge Cases, Security/Validation)
- **Dependencies to Mock:** {MOCKING_REQUIREMENTS} (e.g., Database calls, External APIs, System Clock, Local Storage)

**Execution Guidelines:**
1. Structure all tests using the **Arrange-Act-Assert (AAA)** or **Given-When-Then** design pattern.
2. Use descriptive, self-documenting test names (e.g., `it should throw ValidationError when age is less than 18`).
3. Guarantee coverage across these specific vectors:
   - **Happy Path:** Primary successful workflows and standard inputs.
   - **Boundary & Edge Cases:** Null/undefined values, zero/negative bounds, empty arrays/strings, maximum payload limits.
   - **Failure & Exception Handling:** Network timeouts, invalid state transitions, unexpected throw conditions, unauthorized access.
4. Provide complete mock setups, realistic fixtures/stubs, and proper setup/teardown hooks (`beforeEach`, `afterEach`).
5. Include brief inline comments for non-trivial assertions explaining *why* the test condition matters.

Return fully executable, clean, production-ready test code without missing imports or hand-wavy `// TODO` placeholders.

WHEN_TO_USE:
Use this prompt when you have written a new function, API handler, or module and need immediate, high-coverage test cases before merging. It is ideal for enforcing TDD practices, building refactoring safety nets, and catching subtle edge cases you might have overlooked.

EXAMPLE_INPUT:
**{CODE_OR_FUNCTION}:**
```typescript
async function refundOrder(orderId: string, amount: number, user: UserSession) {
  if (!user || !user.isAdmin) throw new Error("Unauthorized");
  if (amount <= 0) throw new Error("Invalid refund amount");
  const order = await db.orders.findById(orderId);
  if (!order) throw new Error("Order not found");
  if (order.status !== "COMPLETED") throw new Error("Order cannot be refunded");
  
  const paymentRes = await paymentGateway.processRefund(order.paymentIntentId, amount);
  if (!paymentRes.success) throw new Error("Payment gateway failed");
  
  await db.orders.updateStatus(orderId, "REFUNDED");
  return { success: true, transactionId: paymentRes.txId };
}
```
**{TESTING_FRAMEWORK}:** Vitest (TypeScript)
**{TEST_TYPES}:** Unit Tests, Edge Cases, Authorization Checks
**{MOCKING_REQUIREMENTS}:** Mock `db.orders` database calls and `paymentGateway.processRefund` API module.

EXAMPLE_OUTPUT_SUMMARY:
Generates a complete, runnable TypeScript test file using Vitest. It sets up `vi.mock` for the database and payment gateway modules, followed by cleanly grouped `describe` blocks covering authorized/unauthorized users, invalid amount boundaries, order status edge cases (e.g., trying to refund a pending order), failed gateway responses, and successful refund executions with state assertions.

PRO_TIPS:
- Include typescript types/interfaces alongside your target code so the model generates perfectly typed mocks and fixtures.
- If your testing framework supports it (like PyTest parameterized tests or Vitest `test.each`), explicitly ask the prompt to output parameter-driven test cases for boundary values.
- Provide real-world error message strings from your app if you want exact assertion checks on thrown exception messages.
