PROMPT_TITLE: Production-Grade REST API Architect

THE_PROMPT:
Act as a Principal API Architect. Design an intuitive, consistent, and production-ready RESTful API for the following domain:

Domain/Feature: {DOMAIN_OR_FEATURE}
Primary Consumers: {CONSUMER_TYPE} (e.g., Mobile Apps, Third-Party Developers, Internal Microservices)
Key Operations Needed: {KEY_OPERATIONS}
Special Requirements: {CONSTRAINTS_OR_STANDARDS} (e.g., Idempotency, Soft deletes, RFC 7807 errors, Strict backwards compatibility)

Produce a complete API specification including:
1. Resource Hierarchy & URIs: Strict plural noun conventions, proper HTTP verbs (GET, POST, PUT, PATCH, DELETE), and nested paths kept to a maximum of 2 levels.
2. Endpoint Table: Method, Path, Summary, Auth Scope required, and Idempotency guarantees.
3. Payload Contracts: Minimalist JSON request/response schemas for core endpoints, featuring ISO-8601 timestamps, explicit nullability, and strong type typing.
4. Pagination, Filtering & Sorting: Standardized query parameter conventions (cursor vs. page/limit, sort syntax, filter operators).
5. Standardized Error Envelope: A consistent JSON error structure adhering to RFC 7807 (Problem Details) with machine-readable error codes.
6. Edge Case Mitigations: Explicit strategies for optimistic locking (ETags), rate limiting headers, and duplicate submission prevention (Idempotency-Key).

Ensure strict adherence to RESTful principles while avoiding over-engineering.

WHEN_TO_USE:
Use this prompt before writing backend code when creating a new microservice, public API, or refactoring fragmented internal endpoints. It aligns product requirements with battle-tested API design conventions in minutes.

EXAMPLE_INPUT:
Domain/Feature: B2B Subscription & Billing Management
Primary Consumers: Third-Party Developers & Customer Web Portal
Key Operations Needed: Create plan, subscribe organization, upgrade/downgrade tier, preview invoice, list historical invoices with status filter
Special Requirements: RFC 7807 error format, Idempotency keys on charge-triggering mutations, cursor-based pagination

EXAMPLE_OUTPUT_SUMMARY:
A cohesive API design document featuring a detailed endpoint matrix (`/v1/subscriptions`, `/v1/invoices`), complete request/response JSON payloads with typing, a structured RFC 7807 error contract, and operational guidance for handling race conditions and idempotency on billing mutations.

PRO_TIPS:
- Specify your preferred API style (e.g., JSON:API standard, Stripe-like, or Pragmatic REST) in `{CONSTRAINTS_OR_STANDARDS}` for instant aesthetic alignment.
- Ask the model to generate the OpenAPI/Swagger YAML specification immediately after reviewing the design.
- If your system handles massive write volumes, append "Include asynchronous processing patterns (202 Accepted with polling/webhook flow)" to the constraints.
