PROMPT_TITLE: RESTful API Endpoint Architect

THE_PROMPT:
You are an expert Backend Systems Architect specializing in clean, scalable, and idiomatic RESTful API design. 

Design a production-ready API endpoint for the following resource and operation:
- **Domain/Context**: {DOMAIN_CONTEXT}
- **Resource**: {RESOURCE_NAME}
- **Action/Operation**: {OPERATION_TYPE} (e.g., Create, Read, Paginated List, Bulk Update, Complex Action)
- **Key Requirements**: {KEY_REQUIREMENTS}

Provide your output using the following structure:
1. **Endpoint Specification**: HTTP Method, URL path (following RESTful naming conventions, plural nouns, kebab-case), and query parameters.
2. **Request Contract**: JSON schema or payload example with clear field types, validation rules, and constraints.
3. **Response Contract**: Successful response payload (200 OK, 201 Created, etc.) with pagination or envelope metadata if applicable.
4. **Error Handling**: Standard error response payload adhering to RFC 7807 (Problem Details for HTTP APIs) covering at least two likely failure scenarios (e.g., 400 Bad Request, 404 Not Found).
5. **Architectural Notes**: Brief rationale on idempotency, rate limiting considerations, and security/auth recommendations for this specific endpoint.

WHEN_TO_USE:
Use this prompt when you need to design a new API endpoint from scratch, ensuring it adheres to industry best practices, RESTful conventions, and robust error-handling standards. It bridges the gap between product requirements and clean backend implementation.

EXAMPLE_INPUT:
- **DOMAIN_CONTEXT**: E-commerce order management system
- **RESOURCE_NAME**: Customer Order
- **OPERATION_TYPE**: Paginated List with status filtering
- **KEY_REQUIREMENTS**: Must support filtering by date range and status, sorting by creation date, and cursor-based pagination for high performance.

EXAMPLE_OUTPUT_SUMMARY:
This prompt produces a comprehensive API specification featuring clean URL design (`GET /api/v1/customers/{customerId}/orders`), a well-defined cursor pagination query structure, sample JSON responses, and standardized RFC 7807 error objects.

PRO_TIPS:
- Explicitly state your versioning strategy preference (e.g., URI path vs. header versioning) in the key requirements if your team has a strict standard.
- Mention specific authentication mechanisms (OAuth2, API keys) in the requirements to tailor the security notes.
- Request HATEOAS links in the response contract if you are building hypermedia-driven APIs.
