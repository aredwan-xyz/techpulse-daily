PROMPT_TITLE: Production-Ready API Architecture & Contract Designer

THE_PROMPT:
Act as a Principal API Architect. Design a clean, scalable, and consistent API contract based on the following specifications:

- **Domain/Feature**: {DOMAIN_OR_FEATURE}
- **API Architectural Style**: {API_STYLE} (e.g., RESTful, GraphQL, gRPC)
- **Key Business Requirements**: {KEY_REQUIREMENTS}
- **Auth & Authorization**: {AUTH_TYPE} (e.g., JWT Bearer, OAuth2, API Keys)
- **Constraints & Conventions**: {NAMING_AND_CONSTRAINTS} (e.g., camelCase, snake_case, OpenAPI 3.0 target)

Please provide a structured API Specification document including:

1. **Resource Architecture**: Entity hierarchy, URL routing tree, and clear resource boundaries.
2. **Endpoint Map**: Comprehensive table of HTTP methods, paths, summary, and required auth scopes.
3. **Payload Schemas**: Request and Response JSON structures for success cases, including data types, validation rules, and edge-case handling.
4. **Error Schema**: Unified RFC 7807-compliant error payload structure with concrete examples for 400, 401, 403, 404, 409, and 422 errors.
5. **Pagination, Search & Sorting**: Standardized query parameter formats (e.g., cursor vs offset) and default limits.
6. **Resiliency Protocols**: Idempotency key requirements, rate limiting headers, and versioning strategy.

Adhere strictly to industry standards (RESTful noun usage, correct HTTP status codes, safe vs idempotent methods).

WHEN_TO_USE:
Use this prompt when scoping a new service, redesigning legacy endpoints, or establishing a contract between frontend and backend teams. It ensures your API design is standardized, secure, and production-ready before writing code.

EXAMPLE_INPUT:
- **DOMAIN_OR_FEATURE**: E-commerce Customer Subscription Management (Pause, Resume, Upgrade Plan, Invoice History)
- **API_STYLE**: RESTful JSON
- **KEY_REQUIREMENTS**: Allow customers to manage active subscriptions, apply promo codes, and list historical invoices. Support webhooks for billing events.
- **AUTH_TYPE**: OAuth2 JWT Bearer tokens with RBAC (`customer` vs `billing_admin`)
- **NAMING_AND_CONSTRAINTS**: camelCase for JSON fields, plural nouns for endpoints, strict RFC 7807 error formats.

EXAMPLE_OUTPUT_SUMMARY:
A complete, implementation-ready API spec document featuring a full endpoint map (`/v1/subscriptions`, `/v1/subscriptions/{id}/pause`), standard JSON request/response schemas, cursor-based pagination query params, RFC 7807 error definitions, and header protocols for `Idempotency-Key` and `X-RateLimit`.

PRO_TIPS:
- Add *"Format output as OpenAPI 3.0 YAML"* inside `{NAMING_AND_CONSTRAINTS}` if you want a file you can paste directly into Swagger or Postman.
- Mention existing services in your stack so the API design aligns with your current ecosystem patterns.
- Specify soft-delete or hard-delete requirements to get more accurate `DELETE` endpoint schemas.

WORKS_WITH: Claude · GPT-4 · Gemini
