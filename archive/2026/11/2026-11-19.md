## 🎯 The Core Idea (2 sentences)
The researchers built an AI system called UltraTex that creates realistic material maps (like shininess and metallic properties) for 3D objects using just a single photo. By baking actual physics into the image generation process, it stops AI from "guessing" how light interacts with surfaces and starts calculating it accurately.

## 🔍 The Problem They Solved (2 sentences)
Current AI can generate great-looking surface colors from a photo, but it completely chokes when asked to make the object react to new lighting. This happens because a single flat photo tangles up color, shadow, and material type into one messy knot that standard AI can't untangle.

## 💡 The Key Innovation (2-3 sentences)
UltraTex uses a cascaded multi-step approach that separates physics from pure image generation. First, it predicts the surface colors and lighting angles together, then feeds those results alongside material knowledge into a diffusion model to accurately calculate metallic and roughness values. This ensures the generated 3D assets obey real-world optical laws instead of just looking plausible from one specific angle.

## 🛠️ Why Developers Should Care (2 sentences)
If you're building 3D asset generation pipelines for games, e-commerce, or AR/VR, this pipeline delivers ready-to-use PBR textures that actually look correct when players or users move the camera. It eliminates the tedious manual touch-ups currently required to make AI-generated 3D models react properly to game engine lighting.

## ⚡ TL;DR
UltraTex turns a single 2D photo into a fully lit 3D material by forcing AI to understand real-world physics instead of just guessing what looks right.

## 💡 Coding Challenge


TITLE: Session Context Merger
DIFFICULTY: Medium
TOPIC: Hash Maps & Sets
ESTIMATED_TIME: 25 minutes

PROBLEM:
You are building a backend service that aggregates user interaction logs from multiple independent browser tabs into a single unified session history. Each tab sends an array of log entries, but due to network jitter, entries can arrive out of order, be duplicated, or overlap in time.

You are given a list of log arrays (`tabs`), where each log entry is represented as an object (or dictionary) containing:
- `timestamp`: An integer representing millisecond epoch time.
- `action`: A string representing the user's action (e.g., "click", "scroll", "input").
- `target`: A string representing the UI element identifier.

Write a function `mergeSessionLogs(tabs)` that merges all log arrays into a single chronologically sorted list. 
If two or more log entries across different tabs have the **exact same `timestamp`**, `action`, and `target`, treat them as duplicates and keep only one instance. 
Additionally, if entries have the exact same `timestamp` but different actions/targets, sort them deterministically by `action` (alphabetically), and then by `target` (alphabetically).

EXAMPLES:
Input: 
tabs = [
  [
    {"timestamp": 100, "action": "click", "target": "btn-submit"},
    {"timestamp": 105, "action": "input", "target": "field-email"}
  ],
  [
    {"timestamp": 100, "action": "click", "target": "btn-submit"},
    {"timestamp": 102, "action": "scroll", "target": "page-body"}
  ]
]
Output: 
[
  {"timestamp": 100, "action": "click", "target": "btn-submit"},
  {"timestamp": 102, "action": "scroll", "target": "page-body"},
  {"timestamp": 105, "action": "input", "target": "field-email"}
]
Explanation: The duplicate entry at timestamp 100 is removed. The remaining entries are sorted chronologically by timestamp.

Input: 
tabs = [
  [{"timestamp": 50, "action": "view", "target": "dashboard"}],
  [{"timestamp": 50, "action": "click", "target": "nav-home"}]
]
Output: 
[
  {"timestamp": 50, "action": "click", "target": "nav-home"},
  {"timestamp": 50, "action": "view", "target": "dashboard"}
]
Explanation: Both entries share the same timestamp (50). They are sorted lexicographically by action ("click" before "view").

CONSTRAINTS:
- `tabs` contains between 1 and 50 arrays.
- Each array contains between 0 and 1,000 log entries.
- `timestamp` is a non-negative integer up to $10^{13}$.
- `action` and `target` are non-empty strings of length up to 50.

HINT:
Use a Hash Set to store unique composite keys (combining timestamp, action, and target) to eliminate duplicates in $O(1)$ average time per entry. Then, sort the unique entries.

SOLUTION_PYTHON:
```python
def mergeSessionLogs(tabs):
    seen = set()
    unique_logs = []
    
    for tab in tabs:
        for log in tab:
            # Create a unique tuple signature for deduplication
            signature = (log["timestamp"], log["action"], log["target"])
            if signature not in seen:
                seen.add(signature)
                unique_logs.append(log)
                
    # Sort primarily by timestamp, then action, then target
    unique_logs.sort(key=lambda x: (x["timestamp"], x["action"], x["target"]))
    
    return unique_logs
```

SOLUTION_JS:
```javascript
function mergeSessionLogs(tabs) {
    const seen = new Set();
    const uniqueLogs = [];

    for (const tab of tabs) {
        for (const log of tab) {
            // Create a unique string signature for deduplication
            const signature = `${log.timestamp}|${log.action}|${log.target}`;
            if (!seen.has(signature)) {
                seen.add(signature);
                uniqueLogs.push(log);
            }
        }
    }

    // Sort primarily by timestamp, then action, then target
    uniqueLogs.sort((a, b) => {
        if (a.timestamp !== b.timestamp) {
            return a.timestamp - b.timestamp;
        }
        if (a.action !== b.action) {
            return a.action.localeCompare(b.action);
        }
        return a.target.localeCompare(b.target);
    });

    return uniqueLogs;
}
```

TIME_COMPLEXITY: $O(N \log N)$ where $N$ is the total number of log entries across all tabs, dominated by the sorting step. Deduplication takes $O(N)$ time.
SPACE_COMPLEXITY: $O(N)$ to store the set of unique signatures and the resulting array of unique logs.

EXPLANATION:
We flatten the multi-dimensional array of tabs while using a Hash Set to track unique log signatures (`timestamp`, `action`, `target`). This ensures absolute deduplication in linear time relative to the total number of entries. Once duplicates are filtered out, we perform a multi-criteria sort on the deduplicated collection, handling chronological order first, followed by deterministic alphabetical tie-breakers for actions and targets.

FOLLOW_UP:
What if the total number of log entries across all tabs exceeds available RAM (streaming data scenario), and the output must be emitted as an ordered stream with a maximum allowable time-skew (out-of-order buffer window) of $K$ milliseconds? How would you modify your approach using a min-heap?

## What Is It?
Instructor is a Python library built on top of Pydantic that makes it easy to get reliable, structured data—like JSON—out of Large Language Models. Instead of crossing your fingers and crossing out bad regex, it guarantees your LLM outputs match your exact data schemas.

## The Problem It Solves
Before Instructor, developers were writing messy prompt engineering hacks, parsing markdown code blocks, and writing endless try/except loops to catch malformed JSON from LLMs. When the model inevitably missed a field or changed a data type, the whole pipeline broke. Instructor fixes this by using Pydantic to validate outputs, automatically feeding validation errors back to the LLM so it can fix its own mistakes in real-time.

## Why It's Worth 10 Minutes of Your Time
* **Automatic Self-Correction:** If the LLM generates invalid data, Instructor catches the Pydantic validation error and sends it back to the model as a prompt correction, drastically reducing runtime failures.
* **Pure Python DX:** You define your data structures using standard Pydantic classes and type hints, meaning your LLM code looks and feels like normal, type-safe application code.
* **Model Agnostic:** It works seamlessly with OpenAI, Anthropic, Cohere, Gemini, and local models via Ollama, so you aren't locked into a single AI provider.

## Quick Start
```bash
pip install instructor openai
```

```python
import instructor
from openai import OpenAI
from pydantic import BaseModel

# Enable response_model validation
client = instructor.from_openai(OpenAI())

class User(BaseModel):
    name: str
    age: int

user = client.chat.completions.create(
    model="gpt-4o-mini",
    response_model=User,
    messages=[{"role": "user", "content": "Extract: Jason is 25 years old."}],
)

print(user.name)  # Output: Jason (type: str)
```

## Real-World Example
```python
from typing import List
from pydantic import BaseModel, Field
import instructor
from openai import OpenAI

client = instructor.from_openai(OpenAI())

class SentimentAnalysis(BaseModel):
    sentiment: str = Field(description="positive, negative, or neutral")
    confidence: float = Field(ge=0.0, le=1.0)
    key_phrases: List[str]

# Guaranteed to return a valid SentimentAnalysis instance or raise a retry error
analysis = client.chat.completions.create(
    model="gpt-4o-mini",
    response_model=SentimentAnalysis,
    messages=[
        {"role": "user", "content": "The checkout flow was confusing, but support was amazing!"}
    ],
)
print(analysis.sentiment)
```

## Who Should Use It
✅ Perfect for: Developers building production AI agents, data extraction pipelines, or features that need structured JSON from unstructured text.
⏩ Skip if: You are just building a standard chat UI or writing free-form text generation apps where structure doesn't matter.

## The Honest Take
Instructor turns LLMs from unpredictable text-generators into reliable API microservices. It has a tiny learning curve if you already know Pydantic, but it completely changes how safely you can ship AI features to production.
