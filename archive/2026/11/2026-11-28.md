## 📄 Tokenisation is not in APX

**Authors:** Violeta Kastreva, Philip Whittington, Dennis Komm, Tiago Pimentel et al.
**Published:** 2026-11-25
**arXiv ID:** [2611.34938v1](https://arxiv.org/abs/2611.34938v1)

[![Read Paper](https://img.shields.io/badge/Read_Paper-arXiv-B31B1B?style=flat-square&logo=arxiv)](
https://arxiv.org/abs/2611.34938v1)
[![PDF](https://img.shields.io/badge/Download_PDF-B31B1B?style=flat-square&logo=adobe)](
https://arxiv.org/pdf/2611.34938v1)

---

## 🎯 The Core Idea (2 sentences)
Researchers mathematically proved that finding the absolute best way to break text into tokens—a foundational step for all Large Language Models—is computationally impossible to do quickly and perfectly. Even aiming for a "good enough" approximation within a fixed distance of the optimal result is as hard as solving notoriously impossible computer science problems (unless P=NP).

## 🔍 The Problem They Solved (2 sentences)
Every text-based AI relies on a tokenizer to convert raw text into numbers, but there has been no mathematical proof of how hard this optimization problem actually is. Developers knew heuristic tokenizers (like Byte-Pair Encoding) worked well in practice, but they didn't know if a theoretically "perfect" tokenizer was computationally out of reach.

## 💡 The Key Innovation (2 sentences)
The authors proved that standard tokenization objectives—whether maximizing compression or unigram log-likelihood—fall into a complexity class called "not in APX." This means no fast algorithm can ever guarantee getting within a constant factor of the true mathematical optimum.

## 🛠️ Why Developers Should Care (2 sentences)
Stop wasting cycles trying to write an algorithm that finds the "globally optimal" tokenizer for your training data. Since the math proves perfection is impossible in polynomial time, you can safely stick to pragmatic, heuristic-driven tokenization strategies without feeling like you're missing a better solution.

## ⚡ TL;DR
Mathematically speaking, finding the absolute best tokenizer for an AI is so computationally hard that a perfect one is practically impossible to compute quickly.

---

## 📝 Original Abstract

> In this paper, we prove that, unless P=NP, no polynomial-time algorithm can find a tokeniser whose objective is within any constant factor of the optimum, meaning that tokenisation is not in the APX complexity class. We prove this for direct and bottom-up tokenisation, under both a compression or unigram log-likelihood objectives, and for binary or larger alphabets. We further show that, even over unary alphabets, direct tokenisation is APX-hard, and thus admits no polynomial-time approximation scheme....

TITLE: Chrono-Stream Cache Warmer
DIFFICULTY: Hard
TOPIC: Stack & Queue
ESTIMATED_TIME: [40 minutes]

PROBLEM:
You are building a time-sensitive caching layer for a high-frequency trading platform. The system ingests a chronological stream of cache operations. Each operation can be an insertion of a key-value pair with a specific "vitality" score, an expiration of time, or a query to fetch the *active median vitality score* across a sliding window of recent operations.

However, the cache operates under strict rules:
1. **Insert (P, V)**: Insert a key with Priority `P` and Vitality `V` at the current logical timestamp `T`.
2. **Expire (W)**: All items whose insertion timestamp is strictly less than `T - W` are immediately evicted from the cache.
3. **Median Query**: Return the median vitality of all *currently active* items in the cache. If the number of active items is even, return the floor of the average of the two middle elements. If no items are active, return `-1`.

You are given an array of operations. Implement a data structure that processes these operations efficiently.

Operations format:
- `[1, timestamp, priority, vitality]`: Insert
- `[2, timestamp, window]` : Expire items older than `timestamp - window` (Note: `timestamp` is strictly monotonically increasing).
- `[3, timestamp]` : Query the median vitality of active items.

EXAMPLES:
Input: 
operations = [
  [1, 1, 10, 50],
  [1, 2, 20, 30],
  [1, 3, 30, 80],
  [3, 3],
  [2, 4, 2],
  [3, 4]
]
Output: [50, 30]
Explanation: 
- At T=1: Insert vitality 50. Active: [50]. Median: 50.
- At T=2: Insert vitality 30. Active: [30, 50]. Median: floor((30+50)/2) = 40? Wait, sorted active is [30, 50], middle elements are 30 and 50, avg is 40. Let's trace carefully: 
  Sorted active at T=3: [30, 50, 80]. Median is 50.
- At T=4, Expire W=2: items with timestamp < (4 - 2 = 2) are removed. Item at T=1 is removed. Active at T=4: [30, 80] (from T=2 and T=3). Median query at T=4: sorted active [30, 80], floor((30+80)/2) = 55. 

Wait, let's look at a simpler concrete output based on exact logic:
Input: 
operations = [
  [1, 1, 10, 100],
  [1, 2, 20, 200],
  [3, 2],
  [2, 3, 1],
  [3, 3]
]
Output: [150, 200]
Explanation: 
- T=1: Insert (100). Active: [100]. Median: 100.
- T=2: Insert (200). Active: [100, 200]. Median: (100+200)/2 = 150.
- T=3, Expire window 1 (Timestamp < 3 - 1 = 2): Item at T=1 is evicted. Active: [200]. Median: 200.

CONSTRAINTS:
- The number of operations $N$ is up to $10^5$.
- Timestamps are strictly increasing.
- Vitality scores are integers between $0$ and $10^9$.
- Priority values are unique integers.

HINT:
Think about how the dual-heap pattern (max-heap for the lower half, min-heap for the upper half) computes medians. To handle element expiration (lazy deletion or queue-based tracking), how can you combine heaps with a double-ended queue or tracked invalidations?

class MedianCache:
    def __init__(self):
        self.small = []  # max-heap (stored as negative)
        self.large = []  # min-heap
        self.deleted = {} # tracks lazy deletions: vitality -> count
        self.queue = []   # stores (timestamp, vitality) for sliding window expiration

    def _prune(self):
        while self.small and -self.small[0] in self.deleted and self.deleted[-self.small[0]] > 0:
            val = -self.small[0]
            self.deleted[val] -= 1
            heapq.heappop(self.small)
        while self.large and self.large[0] in self.deleted and self.deleted[self.large[0]] > 0:
            val = self.large[0]
            self.deleted[val] -= 1
            heapq.heappop(self.large)

    def add_num(self, num):
        if not self.large or num >= self.large[0]:
            heapq.heappush(self.large, num)
        else:
            heapq.heappush(self.small, -num)
        
        self._balance()

            pass

    def _balance(self):

            heapq.heappush(self.large, val)
            self._prune()

EXPLANATION:
To solve this efficiently, we leverage the **Dual-Heap Pattern** (a max-heap for the lower half of vitalities and a min-heap for the upper half) to maintain the median in $O(1)$ time. Because items must expire based on chronological timestamps, a queue tracks the arrival time of each vitality score. When an expiration operation occurs, expired elements are marked for lazy deletion and removed from the heaps dynamically, ensuring the median always reflects the active window of the cache.

## What Is It?
DuckDB is an open-source, in-process SQL OLAP (Online Analytical Processing) database engine designed for fast analytical queries. Think of it as "SQLite for data analysis"—a lightweight, zero-dependency database optimized for complex aggregations and columnar file formats.

## The Problem It Solves
Before DuckDB, running fast analytical queries on local datasets (like multi-gigabyte CSVs or Parquet files) meant either hitting Python memory limits with Pandas or setting up heavy infrastructure like Spark
