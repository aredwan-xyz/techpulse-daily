## 📄 Tokenisation is not in APX

**Authors:** Violeta Kastreva, Philip Whittington, Dennis Komm, Tiago Pimentel et al.
**Published:** 2026-11-25

## 🎯 The Core Idea
Researchers mathematically proved that finding an optimal text tokenizer in reasonable time is impossible, even if you settle for a rough approximation. This means popular tokenization algorithms like Byte-Pair Encoding (BPE) are fundamentally limited heuristics that can never guarantee a near-optimal vocabulary.

## 🔍 The Problem They Solved
Developers often treat standard tokenizers as "good enough" compression tools without knowing how far they are from the theoretical ideal. This paper solves that open question by proving tokenization belongs to a category of computationally hard problems that cannot be efficiently solved or even tightly approximated.

## 💡 The Key Innovation
The authors mathematically proved that tokenization is "not in APX" (a complexity class for problems that allow fast, guaranteed approximations). This proof holds true across almost all variations of the problem, whether you measure success by file compression or probability (unigram log-likelihood), and regardless of your alphabet size. 

## 🛠️ Why Developers Should Care
Stop spending endless engineering cycles trying to tweak algorithms to find the "perfect" mathematically optimal subword tokenizer—theory proves it doesn't exist. Instead, focus your efforts on task-specific vocabulary tweaks, custom heuristics, or exploring token-free model architectures.

> In this paper, we prove that, unless P=NP, no polynomial-time algorithm can find a tokeniser whose objective is within any constant factor of the optimum, meaning that tokenisation is not in the APX complexity class. # Just

**Category:** Dev Tools
**Link:** [https://github.com/casey/just](https://github.com/casey/just)

[![Repo](https://img.shields.io/badge/View_on_GitHub-181717?style=flat-square&logo=github)](
https://github.com/casey/just)

---

## What Is It?
Just is a modern, language-agnostic command runner that lets you save and run project-specific tasks—functioning like a simpler, cleaner `Make` designed purely for running scripts.

## The Problem It Solves
Before Just, developers relied on `Makefile`s (which are plagued by syntax quirks, tab-indentation requirements, and aren't meant for non-compilation tasks) or cluttered `package.json` scripts that tie non-Node projects to the npm ecosystem. Just fixes the friction of remembering long CLI commands or digging through scattered documentation to figure out how to build, test, and run a project.

## Why It's Worth 10 Minutes of Your Time
1. **Zero syntax surprises:** It uses a clean, intuitive `.justfile` format where indentation doesn't break your execution and comments automatically double as generated help menus.
2. **Polyglot friendly:** You can write your task recipes in Bash, Python, Node, or whatever language your script needs without fighting the tool.
3. **Environment and argument management:** Easily pass arguments to recipes (`just test unit`) and handle `.env` loading out of the box without boilerplate.

## Quick Start
```bash
# Install via Cargo (or Homebrew/Scoop)
cargo install just

# Create a justfile and run your first command
echo "hello:\n\techo 'Hello, World!'" > justfile
just hello
```

## Real-World Example
```makefile
# justfile

# Set the default shell
set shell := ["bash", "-uc"]

# Run the local development stack
dev:
    @echo "Starting databases..."
    docker-compose up -d
    cargo run --bin api-server

# Run tests with an optional filter argument
test filter="":
    cargo test {{filter}}
```

## Who Should Use It
✅ Perfect for: Polyglot developers, teams tired of maintaining clunky `Makefile`s, and anyone who wants a universal task runner across all their repositories.
⏩ Skip if: You are already knee-deep in complex GNU Make compilation dependencies, or you exclusively write JavaScript and are completely happy chaining `npm run` scripts.

## The Honest Take
Just does one thing and does it brilliantly—it replaces your messy shell history and README instruction lists with clean, executable commands. While it's yet another config file to add to your repo, the developer experience payoff makes it an instant-add to every new project I spin up.

## 📋 Developer Briefing

## Daily Security Briefing — November 27, 2026

⚠️ **NVD API Status:** The National Vulnerability Database (NVD) API was unavailable today. Automated scanners relying solely on NVD feeds may not pull the latest updates. You can check [nvd.nist.gov](https://nvd.nist.gov/) directly for critical manual lookups.

---

### Fallback Guidance: Resilient Dependency Management

When centralized vulnerability databases experience downtime, your automated pipeline's scanning capabilities can suffer. Use this time to reinforce your software supply chain practices:

1. **Use Multi-Feed Vulnerability Scanners**
   * **Advice:** Ensure your CI/CD security tools (like Snyk, Trivy, or Grype) draw from multiple vulnerability sources (such as GitHub Advisory Database, OSV, and vendor-specific advisories) rather than relying exclusively on NVD.

2. **Audit and Clean Up Unused Dependencies**
   * **Advice:** The fastest way to reduce your attack surface is to remove what you don't use. Run your package manager's prune/clean commands and audit `package.json`, `requirements.txt`, or `Go.mod` files for abandoned packages.

3. **Verify Lockfile Integrity**
   * **Advice:** Always commit your lockfiles (`package-lock.json`, `Cargo.lock`, `poetry.lock`) to ensure reproducible builds and prevent silent, unvetted minor updates from sneaking into production builds.

---

### 🧠 Security Mindset
**Prune Before You Patch:** Make it a habit to audit and remove unused dependencies *before* performing major version upgrades. Every package you eliminate is one less potential CVE to triage in the future.
